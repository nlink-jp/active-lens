# ADR 0001 — セッション基準の稼働日帰属

**ステータス:** 提案（合意待ち）
**日付:** 2026-07-10
**対象:** `timeline` / `report` / `today` の分析経路（`core/aggregate`、`core/config`、`cmd`）
**対になる ADR:** `active-lens-gui` ADR 0001（描画とホバー）— 両者は同時にリリースする。

---

## 1. 背景

現在の `aggregate.Timeline` は次の順に処理する。

1. `Segments()` がサンプル列を連続した状態スパンへ畳み込む。
2. `splitByDay()` が各スパンを**ローカルのカレンダー深夜 0 時**で切る。
3. `deriveDay()` が**日バケットの内側で**最初と最後の active スパンを探す。

導出が**バケット分割の後**にあるため、稼働マーカーはカレンダー日の
`00:00 – 24:00` から決して外へ出られない。2026-07-09/10 の実データ
（20:44 から翌 00:59 まで作業、就寝、07:26 に再開）はこうなる。

```
2026-07-09   20:44 → 00:00   active 2h 54m   · 2 break(s) 22m
2026-07-10   00:00 → 09:29   active 3h 03m   · 1 break(s) 6h 27m
    break 00:59–07:26 (6h 27m)
```

根本原因はひとつ、症状は3つ。

1. **07-10 の `work_start` が 00:00** — 実在する開始時刻ではなく切断の痕跡。
2. **07-09 の `work_end` が 00:00** — 実際の終了は翌朝 00:59。
3. **夜間の就寝 6時間27分が休憩として計上される。** この away スパンは日バケットの
   初 active と最終 active の間に位置するので、休憩の条件を満たしてしまう。
   3つの中で最も悪い。`span_seconds`、休憩回数、休憩合計のすべてを汚染する。

修正方針を制約する4つ目の事情がある。`activity.Classify` は、ディスプレイが点灯し
マシンが未ロックであれば、**アイドル時間の長さに関係なく** `present` を返す。
`caffeinate` や「ディスプレイを暗くしない」設定で起きたままの Mac は、
`present` を無限に出し続ける。純粋にデータ駆動のセッション規則は、
自力では終端しない活動列に耐えなければならない。

## 2. 決定

日バケット分割の**前に**セッションを導出し、セグメントではなくセッションを
バケットへ入れる。

### 2.1 セッション

**セッション**とは、active（`operating` または `present`）なセグメントを
少なくとも 1 つ含み、`session_gap` 以上の away スパンで区切られた、
極大のセグメント列である。

- `Session.Start` = 最初の active セグメントの開始。
- `Session.End` = 最後の active セグメントの終了。
- 先頭・末尾の away スパンは切り落とす。セッションは活動で始まり活動で終わる。
- 区切りとなった away スパンはどのセッションにも属さない。

### 2.2 論理日

論理日 `D` は半開区間 `[D 04:00, D+1 04:00)`。`day_start_hour`（既定 `4`）で
パラメータ化する。`logical_date(t) = date(t − day_start_hour)`。
`day_start_hour = 0` は論理日をカレンダー日と一致させる。ただし変更前の出力を
再現するわけでは**ない**。セッション化は無条件に効くので、深夜を跨ぐセッションは
0 でも丸ごと残り、開始した日に帰属し続ける。動くのは帰属に使う境界だけである。

### 2.3 帰属

セッションは `logical_date(Session.Start)` の日へ、**分割せず丸ごと**帰属させる。
「夜から未明にかけて」のケースは論理境界を **1 つも跨がない**ので、
開始した日にそのまま残る。

### 2.4 バックストップ

セッションが跨げる論理日境界は**最大 1 つ**。2 つ目の境界に到達した時点で
そこで強制的に閉じ、その瞬間から新しいセッションを開く。

これは §1 の「ディスプレイが眠らない」ケース専用の保険である。任意のセッションを
48 時間未満に抑えるので、暴走した `present` の連続は無限に伸びる代わりに
日サイズの断片へ刻まれる。徹夜（20:00 → 09:00 は境界をちょうど 1 つ跨ぐ）では
発動せず、セッションは丸ごと保たれる。

### 2.5 日マーカー

各論理日について、その日に帰属したセッション群から導く。

- `work_start` = 最初のセッションの開始、`work_end` = 最後のセッションの終了。
- `breaks` = 各セッション内部の休憩の和 — セッション内にある `break_minutes`
  以上の away スパン。セッションを区切る away は必ず `session_gap` 以上なので、
  夜間の就寝がここに現れることはもうない。
- **同じ日のセッション間の空白は休憩ではない。** 日中 5 時間の外出はひとつの
  セッションを終わらせ次を始めるものであり、それを「休憩」と呼ぶのは
  就寝を休憩と呼ぶのと同程度に誤りである。
- `operating_seconds` / `present_seconds` はその日のセッションのセグメントを合計する。

### 2.6 `report` と `today`

`report --by-day` と `today` も論理日でバケットする。01:00 時点の問い合わせが、
継続中の作業を、始まったばかりのカレンダー日ではなく、それが属する日へ帰属させる
ようになる。`ByHourOfDay` は実時刻の時間帯のままにする。時間帯ヒートマップの軸は
実際の時計の時刻でなければ意味を成さない。

セグメントは `emitSplit` により既に時間境界で分割されており、`day_start_hour` は
整数時なので、論理境界を跨ぐセグメントは存在しない。バケットのキーを
`date()` から `logical_date()` へ変えるだけでよい。

### 2.7 生きている端 — now session

セッションが一級市民になった以上、「today」はもうメニューバーの正しい単位ではない。
メニューバーを一瞥するときに問うているのは *「いま続いているこの作業は、いつ始まって、
どれだけ経ったか」* であり、それは日ではなくセッションである。これまで両者が一致して
いたのは、カレンダー日がちょうど 1 つの稼働セッションの外枠を導出していたからにすぎない。
`PopoverView.workSession(_ d: TimelineDay)` は session を名乗りながら day を受け取っている。
本 ADR が取り除くのは、まさにこの偶然の一致である。

**now session** とは、最後の active な瞬間を含むセッションである。
`now − session.End < session_gap` の間は **open**、open かつ現在の状態が `away` の間は
**paused** とする。

生きている端では、セッションが閉じたかどうかを即座に知ることはできない。離席から
30 分の時点で、これが休憩なのか一日の終わりなのかを言い当てられる規則は存在しない。
だがこの不確定性はたった 1 ビットに封じ込められ、境界を汚すことがない。

- セッションの `Start` は決して provisional にならない。
- open なセッションの `End` は、定義上、その最後の active な瞬間である。
- 時間の経過が起こしうるのは `open` の `true → false` だけ。境界が後から動くことはなく、
  表示済みの開始時刻が後で嘘だったと判明することはありえない。

この単位には新しい `now` サブコマンドを充てる。`today` は人間向けの論理日合計として
残す。`today` を再解釈するのではなく `now` を新設するのは、各コマンドがちょうど 1 つの
問いにだけ答える状態を保つためである。

## 3. 設定

```toml
[work]
break_minutes       = 10   # 既存
session_gap_minutes = 240  # 新規: これ以上の away でセッションが切れる
day_start_hour      = 4    # 新規: 0–23、0 ならカレンダー日
```

検証: `0 ≤ day_start_hour ≤ 23`、かつ `session_gap_minutes > break_minutes`
（さもなければ、あらゆる休憩がセッションをも終わらせてしまう）。

## 4. ワイヤ形式

両プロジェクトとも 1.0 前であり、GUI は自前の署名済み CLI を同梱するので、
ペイロードは互換シムなしに変更する。

### 4.1 `timeline --json`

ペイロードのルートに追加: `session_gap_seconds`、`day_start_hour`。

各日に追加: `day_start_unix`（論理日が始まる瞬間 — GUI がチャートのオフセットを
測る原点）、`sessions[]`、`blocks[]`。

`blocks[]` は各セッションをヒットテスト用に敷き詰める。
`{kind: "work"|"break", start_unix, end_unix, start, end, seconds, operating_seconds, present_seconds}`。
ホバーの当たり判定には粗い単位が要るために存在する。GUI 側 ADR を参照。

`segments[]` はその日のセッション**内部**のセグメントのみを持つようになる。
夜間の就寝は away バーとして描かれなくなる。もはやどの日の稼働の一部でもないからだ。
`work_start` / `work_end` は実時刻の `"HH:MM"` 文字列のまま。境界跨ぎの検出は
`work_end_unix` と `day_start_unix + 86400` の比較で行う。

`--days N` フラグは範囲を**論理**上の今日に対して解決する。これがないと、消費側は
`--since` の日付を選ぶためだけに境界規則を再実装する羽目になる。`CLAUDE.md` が
エンジンの持ち物と定めている、まさにその導出である。GUI 側の `calendarSince` を置き換える。

### 4.2 `now --json`

```json
{
  "state": "operating",
  "recording": true,
  "session": {
    "open": true,
    "paused": false,
    "start_unix": 1783..., "start": "20:44",
    "end_unix": 1783...,   "end": "00:59",
    "active_seconds": 10440,
    "operating_seconds": 9180,
    "present_seconds": 1260,
    "breaks": [ { "start": "21:51", "end": "22:01", "seconds": 600 } ]
  },
  "day": { "date": "2026-07-09", "active_seconds": 18720 }
}
```

サンプルが一度も記録されていなければ `session` は null。`day` はそのセッションが
帰属する論理日を持つので、ポップオーバーは二度目の問い合わせなしに二次情報としての
「Today」を表示できる。

## 5. 帰結

**許容する乖離。** `report` の日別合計は各**秒**をそれが属する論理日へ帰属させ、
`timeline` の日別合計は各**セッション**をそれが始まった日へ帰属させる。
両者はセッションが論理境界を跨ぐときにのみ食い違う — 04:00 を貫く徹夜は
`timeline` では開始した日に全量が乗り、`report` では 2 日に分かれる。
これは稼働ログと合計台帳の意図された差であり、糊塗すべき不整合ではない。

**徹夜は始めた夜の日に帰属する。** 20:00 から 09:00 までの作業は開始日の
1 セッションであり、翌朝はその日自身の稼働を持たない。

**病的な最悪ケース。** 自力で終端しないセッションは 2 つ目の論理境界で切られるので、
約 47時間59分に達し、その間に挟まれた論理日は稼働ゼロになる。これはディスプレイが
2 日間眠らず、マシンが一度もロックされない場合にのみ起きる。

**メニューバーの見出し数字はセッションごとにリセットされる。** 見出しの単位を
now session にすると、一晩眠った翌朝 07:26 に Mac を起こした時点の表示は、深夜から
積み上がった時間ではなく `0s` になる。これは変更の目的そのもの（この数字は「この一連の
作業がどれだけ続いているか」に答える）だが、最もよく見られる面での可視的な挙動変更である。
論理日の合計は二次情報の行へ移す。

**open なセッションの `end` は動くが、`start` は動かない。** `now` をポーリングする
消費側は、活動に応じて `end` が進み、離席が `session_gap` を超えた時点で `open` が
`false` に落ちるのを見る。`start` が変わるのを見ることは決してない。

**生サンプルは無傷。** 閾値と境界は集約時に適用されるので、記録済みの全履歴が
移行なしで新しい規則の下に再導出される。

**チャートの列は 24 時間を超えうる。** GUI 側 ADR で扱う。

## 6. 却下した代替案

**`day_start_hour` 単独。** 変更は 2 行で済み、§1 の 3 症状はすべて消える。
しかし境界は固定された実時刻である。05:00 まで及ぶ徹夜は 04:00 で切られ、
症状 1 を 4 時間ずらしてそのまま再現する。パラメータの感度も居心地が悪い —
04:00 か 05:00 かが、まさにユーザーが気にする夜に限って結果を決めてしまう。

**セッション化単独。** 恣意的な時計境界は持たないが、2 つ破綻する。§1 の
「ディスプレイが眠らない」セッションを有界にできない。そして、セッション開始の
**カレンダー**日付で帰属させると、01:00 に始まるセッションが翌日に乗る。
これはまさに本 ADR が除こうとした誤帰属そのものである。

## 7. テスト計画

`core/aggregate` にテーブル駆動で置く。

- カレンダー深夜を跨ぐセッションが分割されず、実際の開始/終了を保つ。
- 夜間の就寝がセッションを終端し、`breaks` に現れない。
- `break_minutes` 未満の短い away は連続稼働に畳まれ、2 つの閾値の間の away は
  休憩になり、`session_gap` 以上の away はセッションを分ける。
- 同一論理日に 2 セッション: セッション間の空白は休憩でない。
- 04:00 を貫く徹夜は境界を 1 つ跨いで丸ごと残る。
- 2 つ目の境界に達したセッションはそこで切られ、残りが新セッションを開く。
- 01:00 に始まるセッションは前の論理日に帰属する。
- `day_start_hour = 0` はセッションを開始時刻のカレンダー日付へ帰属させ、なお深夜跨ぎの
  セッションを丸ごと保つ。
- `session_gap_minutes ≤ break_minutes` は設定エラー。

now session について（`cmd`、時計を注入して）。

- いま active → セッションは open かつ paused でない。
- `session_gap` 未満の離席 → open かつ paused。`end` は最後の active な瞬間に留まり、
  `active_seconds` は増えない。
- `session_gap` 以上の離席 → closed。`start` は以前の呼び出しが報告した値から変わらない。
- サンプルが皆無 → `session` は null。
- `--days N` は `since` をカレンダー上の今日ではなく論理上の今日に対して解決する。
