# ADR 0002 — セッション帰属の日境界を設定可能にする

**ステータス:** 承認
**日付:** 2026-09-17
**対象:** `timeline` / `now` の導出（`core/aggregate`、`core/config`、`cmd`）
**改訂対象:** ADR 0001 §2.3（帰属）、§2.4（バックストップ）、§5（許容する乖離）
**対になる ADR:** `active-lens-gui` ADR 0002 — 両者は同時にリリースする。

---

## 1. 背景

ADR 0001 は、セッションを開始した論理日へ丸ごと帰属させ、日境界で切ることを
しない。個人の記録としてはこれが正しい。01:00 まで及ぶ夜はその晩の仕事であり、
徹夜は始めた夜のものである。

境界が**自分のものでない**とき、これは誤りになる。勤務日が他者によって定義されて
いる場所 — 一日が 05:00 に始まる会社 — では、境界は「その仕事がどの日に計上される
か」を定める規則であって、ログの読みやすさのための経験則ではない。ADR 0001 の下
では 22:00 から翌 09:00 までの作業は丸ごと前日へ帰属する。05:00 以降の時間が、
雇用者の規則では既に終わっていた日へマージされてしまう。

この問題を抱えているのはツールの一部だけである。

| 経路 | 帰属の単位 | 境界が効くか |
|---|---|---|
| `report` / `today` | **秒**をその論理日へ（ADR 0001 §2.6） | 効く |
| `timeline` | **セッション**を開始日へ（§2.3） | 効かない |
| `now` | セッション開始日の日合計（§2.7） | 効かない |

GUI が描いているのは `timeline` と `now` なので、利用者が実際に目にするのは
まさにこのマージである。ADR 0001 §5 はこの乖離を名指しして許容した。本 ADR は
その判断を覆すのではなく、**選択を明示的にする**。正解が「誰の境界か」に依存する
からである。

## 2. 決定

帰属規則を選ぶ enum `work.day_boundary` を追加する。他の導出ノブと同じく集約時に
適用されるので、切り替えれば記録済みの全履歴が移行なしで再導出される。

### 2.1 `session` — 既定、現行のまま

ADR 0001 §2.3・§2.4 そのもの。セッションは開始した論理日へ丸ごと帰属し、切断は
2 つ目の境界のバックストップだけである。

### 2.2 `strict` — 境界がセッションを終わらせる

すべての論理日境界が進行中のセッションを終わらせ、その瞬間から新しいセッションを
開く。各断片はそれぞれの論理日へ帰属する。

直接の帰結が 2 つある。

- `timeline` の日合計が `report` の日合計と一致する。ADR 0001 §5 の乖離は
  `session` モードにしか存在しなくなる。
- セッションは帰属先の論理日を越えられなくなるので、§2.4 のバックストップは発火し得ない。
  条件分岐で無効化するのではなくそのまま残す — limit が違うだけの同じ機構であり、
  経路は 2 本より 1 本のほうが安い。（論理日は 24 時間だが、夏時間の切替を跨ぐ日だけは
  境界が実時刻の時なので 23 時間または 25 時間になる — §5 を参照。）

### 2.3 now セッションも同じ規則に従う

`strict` ではメニューバーの見出しが境界でリセットされる。05:00 に、進行中の作業が
新しいセッションになり、数字は `0s` へ戻る。これは糊塗すべき副作用ではなく狙いその
ものである。勤務日が定義された職場で、一瞥する価値のある数字は「今日に計上される
ほう」だからである。

`now` の `day` は引き続きその時点のセッション開始日の論理日である。`strict` では
セッションが境界を跨げないので、この値は常にそのセッション自身が属する日になる。
ただし `now` が属する日とは限らない — 一晩眠った後、新しい活動が始まるまでは、
その時点のセッションは依然として前日の最後のセッションである（ADR 0001 と同じ）。

### 2.4 切断は隠さず名札を付ける — `carried_in` / `carried_out`

ADR 0001 §6 が「`day_start_hour` 単独」を却下したのは、切断痕が偽の `work_start`
に化けるからだった。この反論は有効であり、`strict` は実際に、前夜から続く日の
`work_start` をちょうど 05:00 にする。答えは切断を避けることではなく、切断だと
言うことである。

各セッションは真偽値を 2 つ持つ。

- `carried_in` — 切断された境界ちょうどから始まった、つまり日が変わった時点で作業が
  既に進行中だった。その `Start` は開始ではなく切断である。
- `carried_out` — 境界の切断で終わった、つまり作業は境界を越えて続いた。

`carried_in` は境界**ちょうど**に始まった場合にのみ立つ。05:00 に離席していて
05:20 に再開したのなら、その日は実在の活動で始まっており、どちらのフラグも立たない
— 切断は名札を付けるべき痕跡を残していない。

日は最初と最後のセッションのフラグを引き継ぐ。両フラグは `session` モードで §2.4 の
バックストップが切ったときにも立つので、既定モードも唯一の人工境界について同じ正直さ
を得る。

## 3. 設定

```toml
[work]
day_boundary = "session"   # または "strict"
```

検証: 綴りはこの 2 つのいずれか。それ以外は設定エラーとする — サイレント
フォールバックはしない。タイプミスが黙って旧来の帰属を維持することこそ、この
オプションが防ごうとしている失敗そのものだからである。

**なぜ既定を `session` のままにするか。** 他方を求めていない利用者の挙動は一切
変わらず、記録済みの徹夜はすべて今日と同じ読み方のまま残り、そして個人利用という
このツールが元々作られたケースについては ADR 0001 が正しかった。職場の境界は
デプロイ側の事実であり、デプロイ側の事実は config に属する。

## 4. ワイヤ形式

両プロジェクトとも 1.0 前であり、GUI は自前の署名済み CLI を同梱するので、
ペイロードは互換シムなしに変更する。

- `timeline --json`: ルートに `day_boundary`。各日・各セッションに `carried_in` と
  `carried_out`。
- `now --json`: セッションに `carried_in`。メニューバーが `0s` の見出しを
  「05:00 に日が変わった」と説明できるようになる（セッションを見失ったようには
  見えなくなる）。ここに `carried_out` は無い — 境界が切ったセッションは決して
  「いまのセッション」にならない。作業はその瞬間に開いた次のセッションへ続くからである。
- `status --json`: `day_start_hour` と `day_boundary` を追加。
- `timeline`（人間向け）: 既定でないときだけヘッダにモードを出す — 既定の規則は報せる
  価値が無く、毎回出る行は誰も読まない（必要なら `doctor` が答える）。引き継いだ日は稼働行へ
  `· continues from previous day` / `· continues into next day` を付ける。記号では
  なく語で書く — この行は既に `→` と `·` で十分に密である。

## 5. 帰結

**`strict` は 2 つの台帳を一致させる。** `timeline` と `report` が徹夜について
食い違わなくなる。それが狙いであり、代償は ADR 0001 が重んじた性質 — 一晩の仕事が
ひとつのオブジェクトであること — である。

**メニューバーは作業中にリセットされる。** `strict` では 05:00、キーボードに手を
置いたまま。その理由を GUI が言えるようにするのが `carried_in` である。

**3 分の日も実在の日である。** 05:03 まで及んだ作業は、境界ちょうどに始まる 3 分の
稼働を持つ日を作り、`carried_in = true` が立つ。厳密な境界とはそういう意味である。

**生サンプルは無傷。** モードを切り替えれば記録済みの全履歴が再導出される。移行する
ものは無く、試してみて失うものも無い。

**夏時間は日を曲げる。曲がるのが正しい。** 境界は実時刻の時なので、DST 切替を跨ぐ
論理日は 23 時間または 25 時間になり、`strict` のセッションも 25 時間に達しうる。秒は
保存され、2 つの台帳も一致したままで、近似なのは上の文中の「24 時間」だけである。
春の切替で設定した時刻が存在しない日には、Go がそれを実在する最も近い瞬間へ解決する
ので、その 1 回だけ境界が 1 時間ずれる。日本に DST は無い。これは他のタイムゾーン向けの
但し書きであって、隠している欠陥ではない。

**窓を読むとは、窓の手前から読むことである。** `--days N` の範囲の最初の瞬間より前に
始まったセッションは丸ごと導出されなければならない。さもないと範囲の最古の日は切断を
実始業として報告する。そこで timeline 経路は `since −（48h + session_gap）`
——その瞬間に触れるセッションを必ず含む幅——からストアを読み、範囲内の日だけを出力する。

## 6. 却下した代替案

**猶予時間**（境界を越える分が N 分未満なら切らない）。値を勝手に丸める余地を、
「こちらが丸めてよい規則ではない」ことだけが価値である規則へ持ち込む案である。
3 分の日は正直であり、3 分が黙って前日へマージされるのは元の欠陥の縮小版にすぎない。

**セッションは丸ごと保ち、日合計だけ切る。** メニューバーは作業中にリセットされ
ないが、`now` と `timeline` が同じ履歴について異なる導出を 2 本持つことになり、
ひとつのセッションが 2 日の台帳に現れる。どこでも同じ規則ひとつのほうが、リセット
の代償に見合う。

**`strict` を既定にする。** 既定として求めている者はおらず、記録済みの徹夜すべての
読み方が変わる。opt-in とする。

**`--day-boundary` CLI フラグ。** ここでの導出ノブはすべて config 専用であり、
ひとつにフラグを付ければノブごとのフラグを招く。`config.toml` を書き換えて再実行
すれば生サンプルから再導出されるので、新しい面を増やさずに同じ実験ができる。

## 7. テスト計画

`core/aggregate` に ADR 0001 のケースと並べてテーブル駆動で置く。

- `strict`: 境界を跨ぐセッションがそこで切られ、各半分がそれぞれの論理日へ帰属し、
  合計が切る前のセッションと一致する。
- `strict` / `session` 両方: 境界がセグメントとセグメントの**間**に落ちるとき——状態変化や
  `max_gap` 分割がちょうど正時に着地した場合——にも切断が起き、その後 limit が進むので
  以降の境界も取りこぼさない。`seg.Start < 境界 < seg.End` の判定だけでは黙って
  素通りするケースである。
- 窓の最古の日が `carried_in` を保つ: 導出は表示する範囲より手前からストリームを読み、
  `sample_count` は範囲内のサンプルだけを数える。
- `strict`: 前半の `End` が境界で `carried_out`、後半の `Start` が境界で
  `carried_in`。
- `strict`: 境界を跨ぐ離席ではどちらのフラグも立たず、各日は実在の活動で始まり終わる。
- `strict`: 同一区間で `timeline` の日合計が `report` の日合計と一致する
  — ADR 0001 §5 の乖離テストの裏返し。
- `session`（既定）: ADR 0001 の全ケースが通り続ける。バックストップの切断で
  `carried_out` / `carried_in` が立つ。
- config: 両方の綴りが解釈でき、それ以外はエラー、未設定は `session`。
- `strict` の `now`: セッションが境界から始まり、`active_seconds` が振り出しに戻り、
  `carried_in` が真で、`day.date` がそのセッションの属する論理日と一致する。
